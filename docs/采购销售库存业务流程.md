# 采购、销售与售后流程

首次使用前，先由管理员建立商户、店铺、仓库及岗位账号，再维护商品 SKU、供应商供货关系和店铺商品映射。下列流程按业务操作顺序阅读；页面入口是否可见取决于账号权限。

## 采购入库

1. 在仓库管理中创建仓库；在供应商档案和商品库建立供应商、商品及 SKU，并维护供应商与 SKU 的供货关系。
2. 在采购订单中选择供应商和 SKU，填写正整数数量及采购价，创建待审核单。总金额由明细计算；已停用供应商、已下架供货明细或父商品不能选用；父商品缺失或供应商归属不一致时同样拒绝创建采购单。
3. 审核采购单，登记供应商发货和收货，再选择仓库生成入库任务。确认收货仅允许已发货采购单及未收货物流记录；取消、未发货或已进入后续阶段的采购单不能通过旧物流记录回退状态。同一采购单只能生成一个整单任务；取消的采购单不能生成任务。
4. 到入库管理按实际收货数量分次入库，并核对 SKU、仓库和库存批次。**生成任务不增加库存，实际入库才增加库存。**

库存采购助手的采购资料可查看包含当前 SKU 的整单物流登记（发货/收货时间、物流公司及运单号），按采购权限和主体范围读取，指定仓库时仅查该仓记录。记录最多200条，未登记不等于未发货；整单记录不能证明本 SKU 的发货数量或预计到货日，不自动计入有效在途。

采购订单和物流入口仅对有对应权限的总部账号开放；查询、创建、审核和处理分别授权，见[账号权限](业务账号权限与数据范围.md)。

## 销售出库

1. 建立商户、店铺和店铺商品，并将店铺 SKU 关联内部 SKU。
2. 创建手工店铺订单，确认同步到订单库；同步失败时使用重新推送，不要重复创建订单。
   创建时传「是否锁库=1」会先校验可用量，再按 SKU 占用库存（`o_goods_inventory.locked_quantity`）；同一 SKU 在一个订单里有多行明细时先合并数量再判断，避免逐行都以为够、合起来超卖。可用量不足直接返回提示、不写订单。锁定记录落在 `o_shop_order_stock_lock`，有效期 30 分钟：取消订单立即释放，未取消也未出库的由定时任务每 5 分钟按过期时间兜底释放。传 0 或不传则不锁，行为与之前一致。
3. 在手动发货中登记快递和运单，在订单备货中生成出库单，再到出库管理执行实际出库并核对批次。

**发货登记和生成出库单不扣库存；实际出库才扣库存。** 入出库按主体和仓库权限限制；库存候选不唯一时须核对归属或选择批次。平台回传由各平台适配层实现，可用性以实际授权的平台为准。

**下单锁定的已知缺口**：实际出库会扣总库存和可用库存，但不会主动核销下单时留下的锁定记录，二者要等到锁定过期（30 分钟）由定时任务收口。也就是说出库后到过期前，可用量会偏小——货已发出，占用还挂着。补齐的做法是在出库单里按订单号核销 `o_shop_order_stock_lock`，当前未做。

## 售后

| 类型 | 处理和库存影响 |
| --- | --- |
| 售前退款、仅退款 | 核对实际退款并登记凭据；不增加库存。 |
| 退货退款 | 生成关联的退货任务；收到并验收后实际入库，核实退款后办结。 |
| 换货 | 退回入库和换出出库分别完成后办结。 |
| 补发 | 生成备货及出库任务，实际出库后办结。 |

本地手工订单与传统 SKU 的售后由系统闭环处理，数量和退款金额受原订单、实际发货及剩余可申请量约束。退款由人工在原渠道完成，系统不自动打款；供应商退货需人工确认收货；平台与云仓售后在其平台侧处理。

## 供应商代发

总部可按商品和数量分配本地仓或已授权且供货关系有效的供应商；供应商实际发货后登记物流。未发货任务可撤销。本地仓须实际出库；供应商发货不扣本地库存，且不会自动通知供应商或回传平台。

订单明细关联商品 SKU 时，已分配或已发货、售后状态未知的明细不能修改；SKU 修改与供应商分配均按订单、明细顺序加锁，避免并发下互相覆盖。

## 部分出库的重复提交与并发冲突

实际出库请求必须携带页面读取到的 `outQuantity`（该明细已出库数量，首次为 0）。服务端锁定主单与明细后比较当前数量；不一致或缺失时拒绝，提示刷新核对。这样部分出库成功但响应丢失后，重发原指令不会再次扣库存。刷新后确认的新操作可携带新进度继续出库。该机制是乐观前置条件与事务行锁结合，不是返回相同成功响应的请求回执机制。

同一明细的多批次出库按顺序提交，前一笔确认成功后递增已出库数量。任一步失败停止后续提交，已成功的批次不会被后续失败回滚；操作人员应刷新单据核对已完成部分。不要将多次 HTTP 请求视为一个原子事务。

## 只读库存对账

具有 `wms:inventory:query` 权限的账号可调用 `GET /api/erp-api/inventory-reconciliation?afterId=0&size=100`，范围按实时业务主体绑定解析，总部、商户、店铺及仓库分别受对应范围约束。单页最多扫描 200 条有效库存，按库存 ID 游标推进；即使本页没有差异，也应使用返回的 `nextAfterId` 继续，直到 `hasMore=false`。

检查项包括数量非负且非空、总量等于可用量加锁定量、批次数量与总量一致，以及批次 SKU、仓库、商户、店铺和库存状态与主记录一致。批次归属异常或数量不明时，不展示可信批次合计。接口返回扫描数量、取数时间及差异原因；同页在只读事务快照内核对，跨页不保证同一快照。

本入口不自动修改库存，不核对孤立批次、业务流水或财务结算。发现差异后，应核查入库、出库、占用和历史修正单据，确定权威来源，再通过受控业务流程修复，不能直接把一侧数量覆盖到另一侧。

## 订单结算事务与失败处理

批量结算每单独立事务，单批最多200单；单单失败先回滚，再返回失败统计，不将事务内部异常吞掉后继续提交。订单先加行锁，已结算订单拒绝重复写入；结算单、成本明细、订单及费用关联必须一起成功。结算事务使用可重复读，费用明细与相关主单在金额归集时锁定；单订单费用明细超过10000条拒绝，主单分批读取。

只有已支付（状态5）的费用参与当前归集和结算状态更新；负向费用调整保留为非零成本明细。取消结算按订单、结算单的顺序加锁，检查关联后显式清空订单和费用的结算ID、时间，费用主单恢复未结算状态。取消或重结算前应核对原费用及业务单据，不能把数据库字段清空当作财务对账完成。

采购单审核、供应商确认、发货及取消采用当前状态条件更新，更新行数为0表示状态竞争失败，调用方需刷新核对，不会覆盖其他并发操作已经提交的状态。

## 结算只读对账

具有 `ai:finance:query` 财务资料权限的账号可调用 `GET /api/erp-api/fms/settlement-reconciliation?afterId=0&size=100`。账号范围由数据库主体绑定解析，总部、商户、店铺分别使用对应范围；供应商和仓库不开放结算对账。单页最多扫描200条结算，正常页同样推进游标，直到 hasMore=false。

差异包括总成本与成本构成不一致、利润与销售额减成本不一致、成本明细合计不一致、金额或明细金额缺失。未知金额不会当作零。接口只返回差异结算标识和原因，不自动修正任何金额；此入口不包括订单关联状态、支付平台账单或孤立成本明细，发现差异后仍需按单据逐项核实。

已有出库批次无法提供总成本或单价乘数量、已有发货记录运费缺失、订单销售金额缺失时，结算明确失败，不将这些未知值当作零。确实免费或零成本的业务应明确记录0，核实后再结算；无关联记录的业务仍需按实际履约模式核查成本覆盖。

当前自动结算成本口径限定本地履约的实际出库批次。供应商代发、商户和云仓任务缺少完整采购成本来源时明确拒绝自动结算，不能把没有本地批次当作零采购成本。需先补充可核实的成本契约和业务录入流程，才可开放对应模式。
